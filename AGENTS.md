# AGENTS.md: rules for every agent working in this repo

This repo holds Half-Life 1 (GoldSrc) deathmatch maps that are **generated by Python**, compiled by our own
BSP compiler, and checked automatically. Two agents (Claude and Codex) and their humans work here together.
Read this whole file before changing anything.

## How work flows

1. **Claim work in an issue first.** Say which map, or which zone of a map, you are taking. Don't start on
   something another agent has claimed and not finished.
2. **Branch + pull request.** Never push to `main`. One topic per pull request.
3. **Never merge your own pull request.** A human approves merges. Review the other agent's pull requests
   when asked: run the checks, look at the preview images, and say what you would change.
4. **CI must be green.** `map-check` builds every map your change touches (all maps if `tools/` changed),
   runs every check, attaches the playable zip, and posts before/after screenshots as a comment.
   Fix red checks before asking for review.
5. **Don't change `tools/` and a map in the same pull request** unless the map change needs the tool change.
   Tool changes affect every map and need the repo owner's approval (see `.github/CODEOWNERS`).

## Avoiding merge conflicts (several agents work here at once)

The repo is laid out so that two agents almost never edit the same file:

- **No central lists.** Maps are discovered from `maps/*/`, zones from `maps/<map>/zones/*.py`, routes and
  views from each zone. Adding a map or a zone never edits a shared file. Don't add hand-maintained lists
  (no map index in the README, no CHANGELOG): release notes come from pull request titles.
- **Work in zones.** A map built with `tools/mapkit.py` is a folder of zone files. Each zone declares its
  `BOUNDS` (the space it may build in), its own `TEXTURES`, `ROUTES` and `VIEWS`. Take a zone, not a map.
  New zone = new file. The build fails if two zones overlap or define the same texture or targetname.
- **Prefix names with the zone.** Textures `HALL_CARPET`, targetnames via `ctx.name("door")` -> `hall_door`.
- **Claim in an issue, not in a file.** Open or comment on an issue ("Claiming maps/foo/zones/street.py"),
  and label it `claimed:claude` or `claimed:codex`. Unclaim by closing or commenting.
- **Branch names:** `claude/<topic>` or `codex/<topic>`. Rebase on `main` before asking for review.
- **Shared files change rarely and alone:** `tools/`, `.github/`, `Makefile`, `AGENTS.md`, a map's
  `zones/_helpers.py`. Open a dedicated pull request for those, claim it with the `tools` label, and only one
  `tools` pull request should be open at a time.
- **Don't reformat files you didn't otherwise change.** No mass renames or style sweeps mixed into map work.
- **The four original maps** (`cagematch`, `justincon`, `battleaxecombatleague`, `prairieloop`) are still
  single-file builds. Converting one into zones is its own claimed pull request; until then, one agent at a
  time works on each of those maps.

## Layout

```
tools/bsp/compile.py        .map + .wad -> .bsp (BSP tree, collision hulls, lighting, sky, pivots, animated textures)
tools/bsp/reader.py         reads a compiled .bsp; shared by every check and the renderer
tools/checks/               structure (engine limits), placements, wiring, walk (route walker)
tools/render/               preview renderer (+ views.py for a map's preview shots)
tools/assets/library.py     texture helpers, base textures, WAD writer
tools/assets/skyfire.py     skybox faces (TGA) + fire sprite
tools/package.py            builds the valve/ layout, .res file and zip
tools/ci/previews.py        CI only: stores screenshots and writes the before/after PR comment
tools/mapkit.py             zone-based map assembly (conflict-free multi-agent maps)
maps/<name>/build.py        generates build/<name>/<name>.map + .wad + valve/ assets (sky, sprites, sounds)
maps/<name>/zones/*.py      zones (maps built with mapkit); files starting with _ are shared helpers
maps/<name>/assets.py       that map's own textures/sprites/sounds (when it has them)
maps/<name>/tests/routes.py walk routes that must stay passable
maps/<name>/tests/views.py  preview camera shots
maps/<name>/map.toml        name, owner, sky, description
build/                      everything generated (git-ignored)
```

## Commands

```
pip install -r requirements.txt        # numpy, scipy, pillow  (+ ffmpeg for videos)
make build MAP=<name>                  # generate, compile, package -> build/<name>/<name>.zip
make test  MAP=<name>                  # structure + limits, placements, wiring, routes
make views MAP=<name>                  # preview PNGs in build/<name>/previews/
make video MAP=<name>                  # walkthrough mp4 + Discord-size copy (if the map has video/walkthrough.py)
make all                               # build + test every map
```

Compile times: small maps take seconds; big ones take 4–10 minutes (lighting is the slow part).

## Hard rules (the checks enforce most of these)

**Engine limits.** Every compiled map must stay under:

| limit | max |
|---|---|
| light samples | 800,000 (engine atlas is ~1M; keep margin) |
| clipnodes | 32,767 |
| nodes | 32,767 |
| leafs | 8,192 |
| faces / marksurfaces / vertexes | 65,535 |
| models (brush entities) | 400 |

If you are near a limit: put pure decoration in a `func_illusionary` (no collision cost), raise texture
scale on big or numerous surfaces (fewer light samples), and avoid many tiny solid brushes.

**Sky.** Sky faces use the texture named exactly lowercase `sky`, and the worldspawn `skyname` must match
the TGA files in `valve/gfx/env/` (`<skyname>rt/bk/lf/ft/up/dn.tga`, 256x256). An uppercase `SKY`
crashes the game when a light touches it.

**Animated textures.** A `+0name` texture needs its `+1name`, `+2name`, … frames in the WAD. The compiler
embeds them all; don't rename frames.

**Rotating parts** (`func_rotating`, `func_door_rotating`, …) need one brush textured `ORIGIN` at the pivot.

**Entities.** Keep visible entities (pickups + sprites + players) under about 200; older game builds
flicker above ~256. Every `target` and `multi_manager` key must name a real `targetname` (wiring check).

**Every new walkable area gets a route** in `tests/routes.py` (the walker steps up at most 18 units, like a
player). If a route fails, fix the map, not the route, unless the route itself is wrong (and say so).

**Spawns and pickups.** Spawns stand at floor + 37 with headroom; pickups sit above the floor, not inside
anything. The placement check verifies both.

**Long jobs.** Any compile, render or video step must run under a timeout and print progress. Never wait
on a silent process; if something stalls, stop it and find out why.

**Content.** Only original artwork, names, text and sounds. No real brands, logos, copyrighted characters,
or crests/flags/religious symbols used as faction emblems. Fonts: only the ones in `tools/assets/fonts/`
(licenses included there).

**Don't commit `build/` or screenshots.** CI produces the zips, previews and videos. Screenshots live on the
`previews` branch, which only CI writes to.

## Coordinates and conventions

- Units are Half-Life units (a player is 32x32x72; eye height ~64; max step 18; jump ~45).
- `z = 0` is ground level unless a map says otherwise in its README. Basements in the existing maps sit at
  floor `-176`.
- Texture names: UPPERCASE, max 15 characters, except `sky` (lowercase) and transparent `{NAME` textures.
- Each map's README documents its own layout (where zones are, who owns them).
- New maps start from `maps/_template/` (zone-based). Prefer adding a zone to growing a giant file.

## When you finish a pull request

Fill in every section of the pull request template (`.github/pull_request_template.md`). Write for a person
who hasn't seen your code or your chat: plain language, what a player will notice and where, and a row per
file or zone saying what changed and why. Paste the limits table and route results. If you couldn't verify
something in the actual game, say so.

**Screenshots are required for every visible change.** You don't upload images yourself: CI renders the map's
views and posts a before/after comment on the pull request (before = `main`, after = your branch, changed views
first). To make sure your change is in it, add a view aimed at it to your zone's `VIEWS` (or
`maps/<map>/tests/views.py`), named for what it shows, e.g. `("pond_from_bridge", eye, target)`. Run
`make views MAP=<map>` and look at the images before pushing. Then list the shots under "Screenshots" in the
description and say what each one shows. Known preview limit: see-through `{` textures (fences, grates)
render as solid blue in screenshots but are see-through in the game.
