# AGENTS.md: rules for every agent working in this repo

This repo holds Half-Life 1 (GoldSrc) deathmatch maps that are **generated by Python**, compiled by our own
BSP compiler, and checked automatically. Two agents (Claude and Codex) and their humans work here together.
Read this whole file before changing anything.

## How work flows: the autonomous loop

Read `docs/pipeline.md` once. Agents run when a human asks them to (there is no always-on worker, to save
credits); the gates, the ledger and merging run on their own in CI.

**When a human gives you a task directly** (the usual way): first open a Task issue for it with the Task form
headings, label it `task` and `claimed:<you>`, then follow steps 3-8 below with `Closes #<that issue>`. Don't
skip the issue: the scope gate holds your PR to its Paths, and the ledger tracks it. Ask the human only when
the task is ambiguous in a way the code can't settle.

**When a human says "do the next thing"**:

1. **Run `make next AGENT=<you>`** (`claude` or `codex`). It gives you ONE action and the lessons to read
   first. Read those lessons. Do that action, nothing else, then run `make next` again or stop.
2. **Work comes from task issues** (the Task form). Claim one by adding the label `claimed:<you>`; the claim
   gate removes it if another claim already covers those paths. Propose new tasks when `next` says `propose`.
3. **Branch `<you>/<topic>`, one task per PR, `Closes #<task>` in the description.** Change only the task's
   paths (plus a lesson in `docs/lessons/`). Never push to `main`.
4. **Adding, renaming or removing a map or a view? Run `make readme`** (CI fails if you forget). It updates the
   main README gallery and the map's screenshot grid; set `hero` in map.toml to choose the gallery shot.
   **Fill every section of the PR template.** Run `make build test views MAP=<map>` before pushing and look
   at the images. Add a named view aimed at every visible change.
5. **The gates decide, CI merges.** The Pipeline comment on your PR lists every gate. Fix ❌ rows and push;
   ⏳ rows clear on their own. When all are ✅, CI merges. You never merge, and you never ask a human to.
6. **Review the other agent's PRs** when `next` says `review`: read the diff, open the screenshot comment and
   look at every changed image, read the check results, then post a comment that ends with:

   ```
   <!-- agent-review -->
   reviewer: <you>
   verdict: approve        (or: changes)
   sha: <the full or 7+ char head sha you reviewed>
   ```

   Approve only what you'd be happy to see in main. With `changes`, list exactly what to fix.
   A push makes old reviews stale (they name a different sha).
7. **Learn.** If a check went red on your PR, or you fix an incident, add a lesson (`docs/lessons/README.md`).
   Update an existing lesson rather than duplicating it.
8. **Incidents first.** If main breaks, an `incident` issue appears and `next` sends every agent there.

**Never** edit `.github/`, `tools/pipeline/`, `AGENTS.md`, `Makefile` or `CLAUDE.md` without a task that a
human has approved: those PRs wait for the `human-approved` label. Never delete or weaken a check to get
green; the ratchet and holdout gates catch it and it breaks trust in the whole system. A human can stop
anything with the `hold` label.

## Avoiding merge conflicts (several agents work here at once)

The repo is laid out so that two agents almost never edit the same file:

- **No central lists.** Maps are discovered from `maps/*/`, zones from `maps/<map>/zones/*.py`, routes and
  views from each zone. Adding a map or a zone never edits a shared file. Don't add hand-maintained lists
  (no map index in the README, no CHANGELOG): release notes come from pull request titles.
- **Work in zones.** A map built with `tools/mapkit.py` is a folder of zone files. Each zone declares its
  `BOUNDS` (the space it may build in), its own `TEXTURES`, `ROUTES` and `VIEWS`. Take a zone, not a map.
  New zone = new file. The build fails if two zones overlap or define the same texture or targetname.
- **Prefix names with the zone.** Textures `HALL_CARPET`, targetnames via `ctx.name("door")` -> `hall_door`.
- **Claim in an issue, not in a file.** Claim a task issue with the label `claimed:claude` or `claimed:codex`;
  its Paths field is what you hold. Claims expire after 48 hours without a PR.
- **Branch names:** `claude/<topic>` or `codex/<topic>`. Rebase on `main` before asking for review.
- **Shared files change rarely and alone:** `tools/`, `.github/`, `Makefile`, `AGENTS.md`, a map's
  `zones/_helpers.py`. Open a dedicated pull request for those, claim it with the `tools` label, and only one
  `tools` pull request should be open at a time.
- **Don't reformat files you didn't otherwise change.** No mass renames or style sweeps mixed into map work.
- **The original maps** (`battleaxecombatleague`, `prairieloop`) are still
  single-file builds. Converting one into zones is its own claimed pull request; until then, one agent at a
  time works on each of those maps.

## Layout

```
tools/bsp/bspc/             the BSP compiler `make build` uses (Go; same output as compile.py, 10-100x faster)
tools/bsp/compile.py        its Python twin, kept as the reference (`make build COMPILER=py`)
tools/bsp/reader.py         reads a compiled .bsp; shared by every check and the renderer
tools/checks/               structure (engine limits), placements, wiring, walk (route walker)
tools/render/               preview renderer (+ views.py for a map's preview shots)
tools/assets/library.py     texture helpers, base textures, WAD writer
tools/assets/skyfire.py     skybox faces (TGA) + fire sprite
tools/package.py            builds the valve/ layout, .res file and zip
tools/ci/previews.py        CI only: stores screenshots, writes the before/after PR comment, visual gate
tools/ci/quality.py         CI only: satisfaction + holdout measurement and the no-regression ratchet
tools/checks/satisfy/       the satisfaction scorer CI uses (Go; same scores as satisfaction.py, 10-20x faster)
tools/checks/satisfaction.py  its Python twin: 0-100 playability score from sampled movement (holdout reuses it)
tools/checks/holdout.py     human-written encrypted scenarios, run only in CI
tools/pipeline/             gates, ledger, `next` scheduler, publisher (see docs/pipeline.md)
docs/lessons/               the knowledge base: one lesson per file, read what `make next` lists
tools/mapkit.py             zone-based map assembly (conflict-free multi-agent maps)
maps/<name>/build.py        generates build/<name>/<name>.map + .wad + valve/ assets (sky, sprites, sounds)
maps/<name>/zones/*.py      zones (maps built with mapkit); files starting with _ are shared helpers
maps/<name>/assets.py       that map's own textures/sprites/sounds (when it has them)
maps/<name>/tests/routes.py walk routes that must stay passable
maps/<name>/tests/views.py  preview camera shots
maps/<name>/map.toml        name, owner, sky, description
go.mod                      one Go module for the repo; every Go program sits next to its Python twin
build/                      everything generated (git-ignored); build/bin/ holds the Go binaries
```

## Commands

```
pip install -r requirements.txt        # numpy, scipy, pillow  (+ ffmpeg for videos); Go 1.24 for the compiler
make build MAP=<name>                  # generate, compile (Go), package -> build/<name>/<name>.zip
make test  MAP=<name>                  # structure + limits, placements, wiring, routes
make views MAP=<name>                  # preview PNGs in build/<name>/previews/
make video MAP=<name>                  # walkthrough mp4 + Discord-size copy (if the map has video/walkthrough.py)
make quality MAP=<name>                # satisfaction score (+ holdout pass rate in CI)
make lint                              # gofmt, go vet, staticcheck
make compiler-parity                   # Go and Python compiler + scorer must agree exactly
make all                               # build + test every map
```

Compile times with the Go compiler: seconds to half a minute per map. If something takes minutes, it's a bug
or you're on the Python path (`COMPILER=py`).

## Working rules we learned the hard way

Each of these cost real time once; the lesson files have the details.

- **Before starting, look for existing work.** Search open and recently merged PRs and issues for the same task.
  Another session may already have done it (a README task was built twice in parallel once).
- **Your task's Paths must cover every file your PR touches.** If the work grows, edit the issue's Paths
  *before* pushing, or the scope gate fails. Claims on overlapping paths lose to the earlier claim; re-add
  your `claimed:` label once the earlier task closes.
- **Rebase on the real latest `main` before opening a PR.** In a git worktree, `git fetch origin main` may only
  update `FETCH_HEAD`: rebase onto `FETCH_HEAD`, and force-push with an explicit lease
  (`--force-with-lease=<branch>:<sha you expect>`).
- **Ports must match exactly, and prove it.** numpy's small dot products are fused multiply-adds in specific
  orders, Python's `math.hypot` is correctly rounded, and `default_rng` is PCG64 via SeedSequence. Measure each
  primitive against the original on thousands of inputs, compare outputs byte for byte (or field by field),
  and keep a parity check in CI. See `tools/bsp/bspc/README.md` and docs/lessons.
- **Prefer comparing to existing artifacts over re-running slow reference code.** A BSP built earlier from the
  same inputs is as good a reference as a fresh 9-minute Python compile.
- **Merges trigger releases in merge order.** Two PRs merging close together release in the order they
  landed, not the order they were opened; check which commit a release came from before calling it wrong.
- **Ask the gates, not your memory.** When a gate fails, read its reason in the Pipeline comment; it has been
  right every time so far (scope, claim overlap, ratchet on deleted tests, missing view names).

## Hard rules (the checks enforce most of these)

**Engine limits.** Every compiled map must stay under:

| limit | max |
|---|---|
| light samples | 800,000 (engine atlas is ~1M; keep margin) |
| clipnodes | 32,767 |
| nodes | 32,767 |
| leafs | 8,192 |
| faces / marksurfaces / vertexes | 65,535 |
| models (brush entities) | 400 |

If you are near a limit: put pure decoration in a `func_illusionary` (no collision cost), raise texture
scale on big or numerous surfaces (fewer light samples), and avoid many tiny solid brushes.

**Sky.** Sky faces use the texture named exactly lowercase `sky`, and the worldspawn `skyname` must match
the TGA files in `valve/gfx/env/` (`<skyname>rt/bk/lf/ft/up/dn.tga`, 256x256). An uppercase `SKY`
crashes the game when a light touches it.

**Animated textures.** A `+0name` texture needs its `+1name`, `+2name`, … frames in the WAD. The compiler
embeds them all; don't rename frames.

**Rotating parts** (`func_rotating`, `func_door_rotating`, …) need one brush textured `ORIGIN` at the pivot.

**Entities.** Keep visible entities (pickups + sprites + players) under about 200; older game builds
flicker above ~256. Every `target` and `multi_manager` key must name a real `targetname` (wiring check).

**Every new walkable area gets a route** in `tests/routes.py` (the walker steps up at most 18 units, like a
player). If a route fails, fix the map, not the route, unless the route itself is wrong (and say so).

**Spawns and pickups.** Spawns stand at floor + 37 with headroom; pickups sit above the floor, not inside
anything. The placement check verifies both.

**Long jobs.** Any compile, render or video step must run under a timeout and print progress. Never wait
on a silent process; if something stalls, stop it and find out why.

**Content.** Only original artwork, names, text and sounds. No real brands, logos, copyrighted characters,
or crests/flags/religious symbols used as faction emblems. Fonts: only the ones in `tools/assets/fonts/`
(licenses included there).

**Don't commit `build/` or screenshots.** CI produces the zips, previews and videos. Screenshots live on the
`previews` branch, which only CI writes to.

## Coordinates and conventions

- Units are Half-Life units (a player is 32x32x72; eye height ~64; max step 18; jump ~45).
- `z = 0` is ground level unless a map says otherwise in its README. Basements in the existing maps sit at
  floor `-176`.
- Texture names: UPPERCASE, max 15 characters, except `sky` (lowercase) and transparent `{NAME` textures.
- Each map's README documents its own layout (where zones are, who owns them).
- New maps start from `maps/_template/` (zone-based). Prefer adding a zone to growing a giant file.

## When you finish a pull request

Fill in every section of the pull request template (`.github/pull_request_template.md`). Write for a person
who hasn't seen your code or your chat: plain language, what a player will notice and where, and a row per
file or zone saying what changed and why. Paste the limits table and route results. If you couldn't verify
something in the actual game, say so.

**Screenshots are required for every visible change.** You don't upload images yourself: CI renders the map's
views and posts a before/after comment on the pull request (before = `main`, after = your branch, changed views
first). To make sure your change is in it, add a view aimed at it to your zone's `VIEWS` (or
`maps/<map>/tests/views.py`), named for what it shows, e.g. `("pond_from_bridge", eye, target)`. Run
`make views MAP=<map>` and look at the images before pushing. Then list the shots under "Screenshots" in the
description and say what each one shows. Known preview limit: see-through `{` textures (fences, grates)
render as solid blue in screenshots but are see-through in the game.
