# AGENTS.md: rules for every agent working in this repo

This repo holds Half-Life 1 (GoldSrc) deathmatch maps that are **generated by Go programs**, compiled by SDHLT
(the standard GoldSrc compiler suite), and checked automatically by Go tools in CI. Claude does the work when
its human asks; CI checks it and merges agent PRs that pass.
Read this whole file before changing anything.

## How work flows

Agents run only when a human asks them to. The human's message is the task: there are no task issues, claims
or gates to satisfy, only the checks in CI.

1. **Look for existing work first.** Search open and recently merged PRs: another session may already be on it.
   Ask the human only when the task is ambiguous in a way the code can't settle.
2. **Read the lessons.** The "Lessons" section below lists every rule we learned the hard way, one line each, by
   area. Read it all (it's short), and open the details of any lesson that touches your task.
3. **Branch `claude/<topic>`, one change per PR.** Never push to `main`. Rebase on the latest `main` first.
4. **Adding, renaming or removing a map or a view? Run `make readme`** (CI fails if you forget). It updates the
   main README gallery and the map's screenshot grid; set `hero` in map.toml to choose the gallery shot.
   To make browsers show new README screenshots after a release, run `make readme V=<commit>` with the
   `previews` commit that stored them (`git log -1 --format=%h origin/previews -- main`) and open a PR.
5. **Fill every section of the PR template.** Run `make build test views MAP=<map>` before pushing and look at
   the images yourself. Add a named view aimed at every visible change: CI's visual gate fails a map change
   that no screenshot shows.
6. **CI merges agent PRs.** `map-check` builds and checks everything; when it passes on a `claude/...` PR,
   `automerge.yml` squash-merges it and starts the release. A human stops that with the `hold` label (or by
   making the PR a draft) and merges their own PRs themselves. If a check fails, fix it and push.
7. **Learn.** Add a lesson in the same PR (format: `docs/lessons/README.md`) when a check went red, when the
   human corrected you, or when something took much longer than it should have. Update or replace an existing
   lesson rather than adding a near-duplicate, and delete lessons that no longer apply. Run `make readme` so the
   index below picks it up, and mention lessons you applied or added in the PR description.

Never delete or weaken a check to get green: fix the map. A check that's wrong gets fixed in its own PR, with
the reason.

## Avoiding merge conflicts (several sessions work here at once)

The repo is laid out so that two agent sessions almost never edit the same file:

- **No central lists.** Maps are discovered from `maps/*/`, zones from the map's `zone_*.go` files, routes and
  views from each zone. Adding a map or a zone never edits a shared file. Don't add hand-maintained lists
  (no map index in the README, no CHANGELOG): release notes come from pull request titles.
- **Work in zones.** A zone-based map (`mapkit.ZoneMap`) is a folder of zone files, `zone_<name>.go`, each
  registering a `mapkit.Zone` from its `init`: its `Bounds` (the space it may build in), its own `Textures`,
  `Routes` and `Views`, and a `Build` function. Take a zone, not a map. New zone = new file. The build fails if
  two zones overlap or define the same texture or targetname.
- **Prefix names with the zone.** Textures `HALL_CARPET`, targetnames via `ctx.Name("door")` -> `hall_door`.
- **Branch names:** `claude/<topic>` (other prefixes count as a human's PR). Rebase on `main` before opening a PR.
- **Shared files change rarely and alone:** `tools/`, `.github/`, `Makefile`, `AGENTS.md`, a zone-based map's
  helper files (the files that aren't `zone_*.go`). Change them in a dedicated pull request, not mixed into map work.
- **Don't reformat files you didn't otherwise change.** No mass renames or style sweeps mixed into map work.
- **The original maps** (`battleaxecombatleague`, `prairieloop`) are hand-written programs, not zone-based.
  Converting one into zones is its own pull request; until then, one session at a time works on each of those
  maps.

## Layout

```
tools/sdhlt.rev             the SDHLT commit `make build` compiles maps with (hlcsg/hlbsp/hlvis/hlrad)
tools/mapkit/               what map programs import: brushes and entities (Valve 220 .map text), zone assembly
                            (ZoneMap), SplitDetail (func_detail), Chunks, Texlights (glowing textures), WAD
                            writer, skybox/sprite/WAV writers, Main (generate, or print routes / views as JSON)
tools/mapkit/paint/         the drawing kit textures use: float colour arrays, aliased shapes, TrueType text,
                            blur and resize (standard library only)
tools/mapkit/textures/      shared base textures, noise helpers and the fonts
tools/mapkit/fonts/         the only fonts textures may use (licences included)
tools/cmd/mapcheck/         `make test`: structure (engine limits), placements, wiring, walk routes;
                            `mapcheck lightbudget MAP.bsp`: light samples per texture
tools/cmd/render/           `make views` (views render concurrently)
tools/cmd/ci/               CI helpers: package (valve/ layout, .res, zip), previews (screenshots, PR comment, visual
                            gate), readme (generated README sections)
tools/bspfile/              Go: reads a compiled .bsp (limits, consistency, hulls); used by the checks and renderer
tools/walker/               Go: the route walker (18-unit steps, free drops)
tools/renderer/             Go: the preview + video renderer (videos import it directly)
docs/lessons/               the knowledge base: one rule per file, indexed in the Lessons section below
maps/<name>/                a Go program (package main): `go run ./maps/<name>` writes build/<name>/<name>.map,
                            .wad and valve/ assets (sky, sprites, sounds); `... routes` / `... views` print its
                            walk routes and preview shots as JSON for mapcheck and the renderer
maps/<name>/zone_*.go       zones (zone-based maps); the map's other .go files are shared helpers
maps/<name>/video/          the map's walkthrough video program, if it has one
maps/<name>/map.toml        name, owner, sky, description
go.mod                      one Go module for the repo (maps, checks, renderer, CI helpers), no dependencies;
                            lint config: tools/.golangci.yml
build/                      everything generated (git-ignored); build/bin/ holds the Go binaries
```

## Commands

```
# needs Go 1.24, git, cmake and a C++ compiler (for SDHLT), and ffmpeg for videos
make build MAP=<name>                  # generate, compile (SDHLT), package -> build/<name>/<name>.zip
make test  MAP=<name>                  # structure + limits, placements, wiring, routes
make views MAP=<name>                  # preview PNGs in build/<name>/previews/
make video MAP=<name>                  # walkthrough mp4 + Discord-size copy (if the map has a video/ program)
make lint                              # golangci-lint (gofmt, go vet, staticcheck, errcheck, unused, ...)
make all                               # build + test every map
```

Build times on GitHub's runners: about a minute for prairieloop, three to four minutes for battleaxecombatleague
(mostly full lighting); `LIGHT=quick VIS=fast` drafts take seconds. Full VIS taking minutes means a map lost
its func_detail split.

CI's checks name what's wrong, and they've been right every time so far.

## Hard rules (the checks enforce most of these)

**Engine limits.** Every compiled map must stay under:

| limit | max |
|---|---|
| light samples | 800,000 (engine atlas is ~1M; keep margin) |
| clipnodes | 32,767 |
| nodes | 32,767 |
| leafs | 8,192 |
| faces / marksurfaces / vertexes | 65,535 |
| models (brush entities) | 400 |

If you are near a limit: put pure decoration in a `func_illusionary` (no collision cost), raise texture
scale on big or numerous surfaces (fewer light samples), and avoid many tiny solid brushes.

**Sky.** Sky faces use the texture named exactly lowercase `sky`, and the worldspawn `skyname` must match
the TGA files in `valve/gfx/env/` (`<skyname>rt/bk/lf/ft/up/dn.tga`, 256x256). An uppercase `SKY`
crashes the game when a light touches it.

**Animated textures.** A `+0name` texture needs its `+1name`, `+2name`, … frames in the WAD. The compiler
embeds them all; don't rename frames.

**Rotating parts** (`func_rotating`, `func_door_rotating`, …) need one brush textured `ORIGIN` at the pivot.

**Entities.** Keep visible entities (pickups + sprites + players) under about 200; older game builds
flicker above ~256. Every `target` and `multi_manager` key must name a real `targetname` (wiring check).

**Every new walkable area gets a route** in the zone's `Routes` (or the map's `routes.go`) (the walker steps up at most 18 units, like a
player). If a route fails, fix the map, not the route, unless the route itself is wrong (and say so).

**Spawns and pickups.** Spawns stand at floor + 37 with headroom; pickups sit above the floor, not inside
anything. The placement check verifies both.

**Long jobs.** Any compile, render or video step must run under a timeout and print progress. Never wait
on a silent process; if something stalls, stop it and find out why.

**Content.** Only original artwork, names, text and sounds. No real brands, logos, copyrighted characters,
or crests/flags/religious symbols used as faction emblems. Fonts: only the ones in `tools/mapkit/fonts/`
(licenses included there).

**Don't commit `build/` or screenshots.** CI produces the zips, previews and videos. Screenshots live on the
`previews` branch, which only CI writes to.

## Coordinates and conventions

- Units are Half-Life units (a player is 32x32x72; eye height ~64; max step 18; jump ~45).
- `z = 0` is ground level unless a map says otherwise in its README. Basements in the existing maps sit at
  floor `-176`.
- Texture names: UPPERCASE, max 15 characters, except `sky` (lowercase) and transparent `{NAME` textures.
- Each map's README documents its own layout (where zones are, who owns them).
- New maps start from `maps/_template/` (zone-based). Prefer adding a zone to growing a giant file.

## References: GoldSrc mapping best practice

Community docs we trust, grouped by the question they answer. Read the relevant one before changing how
maps are built, lit or optimised. Where they disagree with this file or a lesson, this repo wins (our checks
measure our maps); if you think a source shows a rule here is wrong, change the rule in its own PR and cite it.
Most GoldSrc guides assume a hand-built map in Hammer/J.A.C.K.; the ideas carry over to generated maps, the
editor steps don't.

**Compilers (we use SDHLT, pinned in `tools/sdhlt.rev`)**

- SDHLT: https://github.com/seedee/SDHLT (based on VHLT v34; adds tool textures and higher world-size limits)
  and https://developer.valvesoftware.com/wiki/SDHLT
- ZHLT/VHLT docs, which SDHLT inherits (entities, tool textures, command-line options, common compile errors):
  https://thederevtso.github.io/zhlt.info.mirror-unofficial/ and its
  [common problems page](https://thederevtso.github.io/zhlt.info.mirror-unofficial/common-mapping-problems.html)
- VHLT command reference (every hlcsg/hlbsp/hlvis/hlrad flag): https://wiki.svencoop.com/Mapping/VHLT_command_reference
- What each stage does: https://twhl.info/wiki/page/Compile, https://developer.valvesoftware.com/wiki/HLCSG,
  https://developer.valvesoftware.com/wiki/HLBSP

**File formats**

- `.map` (GoldSrc compilers only read Quake 1 Valve220; plane points, texture axes):
  https://developer.valvesoftware.com/wiki/MAP_(file_format)
- `.bsp` v30 lumps (what `tools/bspfile` reads): https://developer.valvesoftware.com/wiki/BSP_(GoldSrc)

**Engine limits and optimisation**

- Compiler charts and per-lump limits (`-chart`, why limits are index sizes, edicts):
  https://twhl.info/wiki/page/Tutorial:_Compiler_charts_and_limits
- Total Map Optimisation, parts 1-3 (wpoly/epoly, VIS and hints, clipnodes, limits, compile parameters):
  https://twhl.info/wiki/page/Total_Map_Optimisation_Part_1_(wpoly,_epoly),
  https://twhl.info/wiki/page/Total_Map_Optimisation_Part_2_(VIS,_Hints), and part 3 in
  https://twhl.info/wiki/page/category:Goldsource_Tutorials+Mapping
- r_speeds and face subdivision: https://twhl.info/wiki/page/Tutorial:_R_Speeds and
  https://twhl.info/wiki/page/VERC:_Advanced_r_speeds_Control
- Visibility, func_detail and hint brushes: https://developer.valvesoftware.com/wiki/BSP_Map_Optimization,
  https://twhl.info/wiki/page/VERC:_Hint_Brush_Tutorial (design real vis blockers first; hints refine them)
- Leaks (a map must be sealed; VIS and RAD refuse to run on a leak):
  https://twhl.info/wiki/page/Tutorial:_How_to_fix_those_leaks, https://developer.valvesoftware.com/wiki/Leaks

**Scale and player movement** (what `tools/walker` and the placement checks model)

- https://developer.valvesoftware.com/wiki/GoldSrc_Dimensions and https://twhl.info/wiki/page/Tutorial:_Dimensions:
  step 18, jump 45, crouch-jump 63, player 32x32x72, pass-through gap 33, crouch clearance 37, walk clearance 73.
- https://twhl.info/wiki/page/VERC:_Half-Life_Unit_To_Real-Life_Unit_Conversion: there's no exact real-world

**Lighting**

- https://twhl.info/wiki/page/Tutorial:_The_Complete_Guide_to_Lighting (light entities, texture lights, styles,

- https://twhl.info/wiki/page/Tutorial:_Half-Life_Deathmatch_mapping (a layout new players can learn quickly;

- Index of every GoldSrc mapping tutorial: https://twhl.info/wiki/page/category:Goldsource_Tutorials+Mapping

## When you finish a pull request

Fill in every section of the pull request template (`.github/pull_request_template.md`). Write for a person
who hasn't seen your code or your chat: plain language, what a player will notice and where, and a row per
file or zone saying what changed and why. Paste the limits table and route results. If you couldn't verify
something in the actual game, say so.

**Screenshots are required for every visible change.** You don't upload images yourself: CI renders the map's
views and posts a before/after comment on the pull request (before = `main`, after = your branch, changed views
first). To make sure your change is in it, add a view aimed at it to your zone's `Views` (or
the map's `views.go`), named for what it shows, e.g. `{Name: "pond_from_bridge", Eye: ..., Target: ...}`. Run
`make views MAP=<map>` and look at the images before pushing. Then list the shots under "Screenshots" in the
description and say what each one shows. Known preview limit: see-through `{` textures (fences, grates)
render as solid blue in screenshots but are see-through in the game.
